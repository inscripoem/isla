# M1 kokoro generated-WAV browser smoke harness

An isolated, loopback-only browser harness that drives the real M1 browser
playback controller (`createPlaybackController`) and DOM media driver
(`createDomMediaDriver`) against one generated kokoro WAV fixture.

This is a **test fixture backend and manual browser harness**. It is not M5
production HTTP wiring, and it exposes no generic file-serving endpoint.

## Prerequisites

The fixture must already exist at the exact cache path
`repo/.cache/audio/kokoro-smoke.wav`, freshly generated by the separate kokoro
CLI. The harness reads and validates the current bytes at request time; it does
**not** fall back to any older fixed asset, and there is no snapshot size, hash
or duration baked into the code. If the file is missing, malformed or changes
between the metadata and audio requests, the run reports an honest failure.

Current expected format: 24 kHz mono IEEE-float (32-bit) WAV, `WAVE_FORMAT`
tag 3.

Each run fetches the fixture once, validates the exact bytes against the
metadata and freezes them as a single immutable `Blob`. Both controlled-ref
plays use that same verified `Blob`, so the audio that is played is exactly the
audio the report hashed and measured.

## Start the fixture server

From the repository root:

```
pnpm exec vite --config test/live/kokoro-browser.config.ts --host 127.0.0.1 --port 4188 --strictPort
```

The server binds loopback only; a non-loopback `--host` override is refused.
The default port is 4188.

Open:

```
http://127.0.0.1:4188/kokoro-browser.html
```

## Using the harness

- Click the button labelled **Run browser smoke** (`id="run"`).
- Read the JSON result in the `pre` element `id="result"`.

## Fixture routes

Only two fixed GET routes exist, and only the exact raw pathname is accepted:

- `GET /__kokoro_fixture/metadata` — JSON with `sha256`, `byteLength`,
  `sampleRate`, `channels`, `bitsPerSample`, `floatFormat`, `frameCount` and
  `durationMs`, derived from the current RIFF bytes.
- `GET /__kokoro_fixture/audio.wav` — the current WAV bytes
  (`Content-Type: audio/wav`).

Both set `Cache-Control: no-store`. Unsupported methods, query strings, path
variants and percent-encoded variants are rejected. Other requests are checked
against a fail-closed allowlist limited to the harness HTML/client, Vite's
client/env endpoints, real optimized dependency assets and the browser-safe
`src/performance/browser` and `src/contracts/app` source graph.

## Result JSON

`pre#result` is overwritten on every run: it starts from `{"status":"READY"}`
and while running shows `{"status":"RUNNING"}`, so a previous `PASS` is never
left behind after a failed rerun. The final report has `status`
`PASS` or `FAIL` and includes:

- `checks`: per-check `id`/`ok`/`detail` outcomes.
- `fixture.metadata`: the server metadata, plus `browserSha256` and
  `browserByteLength` computed in the browser with `crypto.subtle`.
- `decodedAudio`: the actual `AudioContext.decodeAudioData` duration, sample
  rate and channel count, compared against `frameCount`/`sampleRate` with a
  tolerance of two decoded-rate samples plus 1 ms.
- `receipts.observer`: the single observer's emitted receipts; `naturalExecute`,
  `stopExecute` and `stopCancel` appear separately as raw return values.
- `naturalRun` / `stopRun`: output ids, native event records (with timestamps
  and `isTrusted`), observer stages, and DOM cleanup state (paused, `src`
  removed, `currentTime` reset).
- `resources`: object-URL create/revoke counts and live URLs, lease
  resolve/release counts, `AudioContext` close state and controller disposal.

## Scope limits

Playback is muted. This validates the browser media API path only (`play`,
`playing`, `ended`, `cancel`, cleanup). It does **not** prove acoustic speech or
silence, loudness, latency or real network timing, and it is not full product
I2 acceptance.

Run this harness explicitly after the live worker smoke produces the WAV. Its
source and build checks in this repository do not establish a browser run and do
not by themselves claim browser success.
